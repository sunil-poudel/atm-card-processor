## 1. Spring Boot & Java Core

### Q1: How does Spring Boot auto-configuration work under the hood?
**Answer:**
Spring Boot auto-configuration is driven by the `@EnableAutoConfiguration` annotation (included in `@SpringBootApplication`). During application context startup:
1. Spring Boot scans `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` across all JAR dependencies on the classpath.
2. Each auto-configuration class is evaluated against conditional annotations:
   - `@ConditionalOnClass`: Verifies required classes are on the classpath (e.g., `DataSourceAutoConfiguration` checks for `DataSource.class`).
   - `@ConditionalOnMissingBean`: Ensures Spring only defines default beans if the user application hasn't already defined custom beans of that type or name.
   - `@ConditionalOnProperty`: Activates beans conditionally based on environment configuration values.
3. Classes are ordered using `@AutoConfigureOrder`, `@AutoConfigureBefore`, or `@AutoConfigureAfter`.
4. In ATM Card Processor, custom configurations (e.g., `TimeConfig`, `SecurityConfig`, `OpenApiConfig`) override default configurations, ensuring deterministic initialization without magical classpath behavior.

### Q2: What does `@Transactional` really do, and what are its common failure modes (proxies, rollback rules, self-invocation)?
**Answer:**
`@Transactional` uses Spring AOP to wrap target methods with a transaction interceptor (`TransactionInterceptor` managing a `PlatformTransactionManager`):
- **Dynamic Proxies:** Spring creates a JDK dynamic proxy (for interfaces) or CGLIB subclass proxy (for concrete classes). The proxy opens a database transaction, invokes the target method, and commits or rolls back based on the outcome.
- **Rollback Rules:** By default, Spring only rolls back transactions on unchecked exceptions (`RuntimeException` and `Error`), not checked exceptions (`Exception`). In ATM Card Processor, all domain errors inherit from unchecked `ApiException`, guaranteeing rollbacks when business failures bubble up.
- **Self-Invocation Failure:** If a method `foo()` inside class `A` calls `@Transactional public void bar()` within the same class `A` via `this.bar()`, the proxy is bypassed. No transaction is opened for `bar()`.
- **Solution:** Transaction boundaries must be invoked across bean references (e.g., calling `LedgerService` from `AuthorizationService`) or refactored into distinct service components.

### Q3: Why prefer constructor injection over field injection (`@Autowired`)?
**Answer:**
Constructor injection is strictly enforced in ATM Card Processor because:
1. **Immutability:** Dependencies can be declared `final`, ensuring thread safety and preventing accidental reassignment after bean construction.
2. **Compile-Time Safety & Null-Pointer Prevention:** The compiler and JVM guarantee that an object cannot be constructed without satisfying all required dependencies. Field injection allows objects to exist in partially initialized, broken states.
3. **Pure Unit Testing:** Classes with constructor injection can be tested in standard JUnit tests by instantiating them with plain Java mocks (`new AuthorizationService(...)`), without needing heavy Spring test contexts or reflection hacks.
4. **Circular Dependency Detection:** Constructor injection exposes circular dependencies immediately at startup time, forcing clean architectural boundaries rather than hiding cyclical coupling.

### Q4: Why use `spring.jpa.hibernate.ddl-auto=validate` with Flyway instead of `ddl-auto=update`?
**Answer:**
- `ddl-auto=update` or `create-drop` executes non-deterministic, uncontrolled schema alterations generated by Hibernate's entity introspection. In production:
  - It cannot safely rename columns or drop foreign keys without risking data loss.
  - It does not support complex index creation (such as partial unique indexes or functional expressions).
  - In a cluster with multiple rolling pods, concurrent Hibernate schema alterations lead to schema race conditions and table deadlocks.
- **Flyway Database Migrations:** Versioned, immutable SQL scripts (`V1__...sql`, `V2__...sql`) are committed to version control. Migrations are executed linearly, tracked in `flyway_schema_history` with SHA-256 checksums, and executed in transactions.
- `ddl-auto=validate` verifies that the JPA entity mappings strictly match the actual database schema generated by Flyway without making any modifications. If a mismatch exists, the application safely halts during boot before processing any traffic.

### Q5: What is the JPA N+1 query problem, and how is it prevented in this codebase?
**Answer:**
The N+1 problem occurs when an application fetches $N$ entities in one query, and subsequently triggers $N$ additional database queries when accessing lazy-loaded associations (e.g., fetching 50 transactions, and then querying the `Card` entity 50 times in a loop).
**Prevention in ATM Card Processor:**
1. **Explicit Entity Graphs & JOIN FETCH:** Repositories use `JOIN FETCH` queries or `@EntityGraph` when associations must be hydrated in bulk.
2. **DTO Projections:** Financial reports and transaction listings project directly into flat records using JPQL constructors or native PostgreSQL queries (e.g., `ReportQueryRepository`), bypassing entity hydration completely.
3. **Automated N+1 Regression Testing:** `QueryCountIT` utilizes QuickPerf / Hibernate statement interceptors to assert that fetching pages of transactions or cards executes strictly a constant number of SQL queries regardless of page size.

### Q6: Why is `spring.jpa.open-in-view=false` essential in production financial systems?
**Answer:**
`spring.jpa.open-in-view` (OSIV) binds a Hibernate `Session` / database connection to the entire thread lifecycle of an HTTP request, from incoming filter to JSON serialization completion:
1. **Connection Pool Exhaustion:** If a slow client takes 3 seconds to download a large JSON response, or an external payment API call is made during the controller execution, the database connection is held open and idle. Under high concurrency, the HikariCP connection pool exhausts rapidly, causing system-wide cascading outages.
2. **Silent Performance Traps:** OSIV allows controllers and JSON serializers (Jackson) to trigger lazy-loading database queries outside of transaction boundaries, hiding N+1 problems until production load spikes.
3. **Strict Separation:** Disabling OSIV forces all database access to happen strictly inside `@Transactional` service methods. When a service method returns, the connection is instantly returned to the pool, and controllers serialize detached, immutable DTO records.

### Q7: What is the architectural difference between `@WebMvcTest` and `@SpringBootTest`?
**Answer:**
- `@WebMvcTest`: Slices the Spring context to test only the web layer (controllers, custom formatters, filters, controllers advice, and security filters). Service and repository beans are not created; instead, they are mocked via `@MockitoBean` or `@MockBean`. It boots in milliseconds and validates HTTP status codes, JSON serialization, RFC 9457 Problem Details error formats, and request validation.
- `@SpringBootTest`: Boots the entire application context, including all services, repositories, JPA entities, and database datasources. In ATM Card Processor, full integration tests (`*IT.java`) run with `@SpringBootTest(webEnvironment = RANDOM_PORT)` against a real PostgreSQL container or instance, verifying the end-to-end stack including database locking, Flyway migrations, and transaction rollbacks.

### Q8: What problem does Testcontainers solve that H2 in-memory databases cannot?
**Answer:**
H2 does not implement PostgreSQL dialect semantics, leading to false confidence:
1. **PostgreSQL-Specific Syntax & Types:** H2 does not natively support UUIDv7, JSONB operators, `TIMESTAMPTZ`, PostgreSQL table locking (`SELECT ... FOR UPDATE`), or PostgreSQL interval arithmetic (`INTERVAL '30 days'`).
2. **Concurrency & Locking Realism:** H2's lock manager behaves fundamentally differently from PostgreSQL MVCC. Row-level pessimistic locking, deadlocks, and `FOR UPDATE SKIP LOCKED` cannot be realistically tested in H2.
3. **Migration Consistency:** Flyway scripts written for PostgreSQL often fail on H2 or require divergent SQL scripts. Testcontainers runs real Dockerized PostgreSQL instances, guaranteeing 100% parity between local tests, CI pipelines, and production environments.

### Q9: Why use Java 21 Records for DTOs but standard classes for JPA Entities?
**Answer:**
- **Records for DTOs:** Records provide compact, immutable carrier objects with compiler-generated `equals()`, `hashCode()`, `toString()`, and canonical constructors. Because DTOs represent immutable snapshots of data transferred across HTTP or service boundaries, records prevent accidental mutation and guarantee thread safety.
- **Classes for JPA Entities:** JPA/Hibernate relies on mutable entity state for dirty checking, proxy generation, and lazy loading. Furthermore:
  - JPA requires a no-args constructor (at least package-private) and non-final fields to hydrate entities through reflection.
  - Entities have domain identity based on their primary key (`id`), whereas records have value-based identity based on all component fields.

### Q10: Why did we intentionally avoid Project Lombok in this project?
**Answer:**
1. **Java 21 Modernization:** Modern Java includes records, text blocks, pattern matching, and sealed types, removing the vast majority of boilerplate that Lombok previously solved.
2. **Annotation Processing Fragility:** Lombok modifies the compiler's Abstract Syntax Tree (AST) using private javac APIs. It frequently breaks or delays upgrades during major Java (e.g., Java 21/25) or Spring Boot upgrades.
3. **Debugging and Static Analysis Transparency:** Generated code from Lombok can obscure stack traces, hinder bytecode instrumentation tools (JaCoCo coverage metrics), and cause subtle bugs in JPA entity equals/hashCode implementations. Explicit code with constructor injection is clear, auditable, and easily parsed by ArchUnit.

## 2. Money, Concurrency & Correctness

### Q11: Why represent money as `long` minor units rather than `double`, `float`, or `BigDecimal`?
**Answer:**
- **Floating-Point Imprecision (`double`/`float`):** IEEE 754 floating-point types cannot accurately represent base-10 fractions (e.g., `0.1 + 0.2 = 0.30000000000000004`). In financial systems, cumulative round-off errors lead to balance drift, broken audit reconciliation, and regulatory non-compliance.
- **Performance & Simplicity over `BigDecimal`:** While `BigDecimal` prevents precision loss, it is an immutable heap-allocated object requiring method calls (`add()`, `subtract()`, `compareTo()`) and explicit rounding mode specifications. A primitive `long` represents the exact integer count of the currency's minor units (e.g., NPR cents or USD cents):
  - Incurring zero object allocation overhead.
  - Supporting fast, hardware-native CPU arithmetic.
  - Eliminating rounding ambiguity during additions and subtractions.
  - Mapping cleanly to SQL `BIGINT`.

### Q12: What is an append-only ledger, and why is the card balance never mutated directly?
**Answer:**
In double-entry accounting and payment processing, balances are derived quantities, not source-of-truth states:
- If a card balance is updated directly (`UPDATE card SET balance = balance - 500`), the historical context is destroyed. If an auditor asks why the balance changed, there is no immutable audit trail.
- **Append-Only Architecture:** Every financial movement creates an immutable `LedgerEntry` recording the exact delta (`amount_minor`), the resulting balance after the operation (`balance_after_minor`), the entry type (`DEBIT`, `CREDIT`, `REVERSAL`), and references to the authorizing transaction.
- **Enforced Single Writer:** Only `LedgerService` has authority to insert ledger entries and update the cached `balance_minor` column on the `Card` entity within the same locked transaction. The ledger can never be updated or deleted (`ON DELETE RESTRICT`, database triggers, ArchUnit rules).

### Q13: How is double-spending prevented under high concurrency? Explain Pessimistic Locking vs Optimistic Locking trade-offs.
**Answer:**
- **Optimistic Locking (`@Version`):**
  - Detects concurrent updates at commit time by verifying the version column hasn't incremented.
  - *Trade-off in Payments:* If 50 payment requests hit the same card simultaneously, 49 requests will fail with `OptimisticLockException` and require costly retries. Under high contention, optimistic locking leads to severe transaction churn and elevated latency.
- **Pessimistic Row Locking (`SELECT ... FOR UPDATE`):**
  - ATM Card Processor uses `cardRepository.findByIdForUpdate(cardId)`, acquiring an exclusive row-level write lock in PostgreSQL.
  - Incoming authorization requests for the same card queue deterministically at the database level.
  - The transaction reads the exact current balance and daily usage counter, performs authorization checks, writes the ledger entry, updates the cached card balance, and commits.
  - The lock is held for mere milliseconds, completely eliminating double-spend races without transaction aborts.

### Q14: What is idempotency, and how do the key, scope, and SHA-256 payload fingerprint work together?
**Answer:**
Idempotency guarantees that an API request can be repeated multiple times without changing the system state beyond the initial application.
1. **Client Header:** The client supplies an `Idempotency-Key` (e.g., UUIDv7) in the HTTP header.
2. **Scope Partitioning:** The key is scoped per client/card endpoint: `(scope, idempotency_key)` has a unique index in the `idempotency_record` table.
3. **Payload Fingerprinting:** The request body is canonicalized and hashed via SHA-256 (`payload_hash`).
4. **Resolution Sequence:**
   - If the key is new: A record is reserved in the database with status `PENDING`. The business logic executes, saves the response status and body, and marks it `COMPLETED`.
   - If the key exists with the **identical** payload hash: The server immediately returns the cached HTTP response with the header `Idempotent-Replayed: true`. No card balance or ledger mutation occurs.
   - If the key exists with a **different** payload hash: The server rejects the request with HTTP 409 Conflict (`IDEMPOTENCY_CONFLICT`), preventing parameter tampering or key collision.

### Q15: What happens when a network timeout occurs between client and server during authorization?
**Answer:**
If the client times out while waiting for an authorization response, it cannot know whether the server processed the payment, debited the balance, or failed before reaching the database:
- Because the client supplied an `Idempotency-Key`, its automated retry mechanism safely resends the exact same request with the same header.
- The server checks the idempotency store:
  - If the original request completed successfully before the network drop, the cached approval or decline response is returned immediately with `Idempotent-Replayed: true`.
  - If the original request rolled back due to an error, the retry executes fresh against the current card state.
  - If the original request is still in flight (status `PENDING`), the server returns HTTP 409 or HTTP 425 to signal concurrent execution in progress.

### Q16: How would this architecture adapt from single-message authorization to a two-phase clearing/settlement cycle?
**Answer:**
In dual-message card networks (Visa/Mastercard):
1. **Authorization (Phase 1):** Funds are not moved directly to the merchant. Instead, an `AuthorizationHold` is created, which decrements the card's `available_balance` while leaving the `ledger_balance` unchanged. The hold has an expiry (e.g., 7 days).
2. **Presentment / Settlement (Phase 2):** Days later, the merchant bank submits an ISO 8583 clearing record. The processor matches the clearing record to the authorization hold:
   - If the settled amount equals the authorized amount: The hold is released, and `LedgerService` writes a formal `DEBIT` ledger entry reducing the `ledger_balance`.
   - If the merchant never settles: An automated background sweeper expires the hold, restoring `available_balance`.
   - In ATM Card Processor's prepaid model, authorization and clearing are unified into immediate single-message settlement, but the ledger structure is directly extensible to hold-balance models.

## 3. Security, Cryptography & Compliance

### Q17: How does JWT authentication paired with rotating refresh tokens work in this system?
**Answer:**
1. **Short-Lived Access Token:** Upon login, the user receives an asymmetric RS256/symmetric HS256 signed JWT with a 15-minute expiration time. This token contains user claims, roles, and subject ID.
2. **In-Memory Storage:** The Angular frontend keeps the access token strictly in browser memory (inside a private TypeScript service variable), never writing it to `localStorage` or `sessionStorage` where it would be vulnerable to XSS exfiltration.
3. **Rotating Refresh Token:** A cryptographic random token with a 7-day expiration is returned as an `HttpOnly`, `SameSite=Strict`, `Secure` cookie.
4. **Silent Refresh:** When the access token expires, an HTTP interceptor transparently issues a `POST /api/v1/auth/refresh` request using the cookie, obtaining a fresh access token and a brand-new refresh token while invalidating the old refresh token.

### Q18: What is Token Family Reuse Detection, and what attack does it neutralize?
**Answer:**
Token family reuse detection protects against compromised refresh tokens:
- Every refresh token belongs to a persistent `token_family_id`.
- When a client uses refresh token $T_1$, the server marks $T_1$ as used and issues $T_2$ within the same family.
- If an attacker intercepts $T_1$ and attempts to use it after the legitimate client has already exchanged it for $T_2$, the server detects that $T_1$ has already been consumed.
- **Automated Revocation:** The server flags this as a security breach, revokes the entire `token_family_id`, and invalidates all active sessions for that user. The legitimate user is prompted to re-authenticate, and an immediate audit alert is logged.

### Q19: Why are API client keys hashed with SHA-256, but staff user passwords require BCrypt?
**Answer:**
- **Entropy & Precomputation:** Human passwords have low entropy (typically dictionary words or predictable patterns). An attacker with a GPU cluster can compute billions of fast SHA-256 hashes per second to crack passwords via rainbow tables or brute force. Therefore, passwords require a slow, computationally expensive, salted, memory-hard key derivation function like **BCrypt** with a configurable work factor (cost 12).
- **High-Entropy Machine Keys:** Machine API keys are generated with 256 bits of cryptographically secure randomness (`SecureRandom`). Because of the astronomical keyspace ($2^{256}$), brute-force dictionary attacks are mathematically infeasible. Fast cryptographic hashing with **SHA-256** allows sub-millisecond database lookups and authentication per API request without imposing massive CPU denial-of-service overhead on the server.

### Q20: How are Primary Account Numbers (PANs) secured using AES-256-GCM and Blind Indexing?
**Answer:**
PCI-DSS strictly prohibits storing plaintext PANs:
1. **Encryption at Rest (AES-256-GCM):** The full PAN is encrypted using AES-256 in Galois/Counter Mode (GCM), providing authenticated encryption with associated data (AEAD). The card's UUID (`cardId`) is supplied as Additional Authenticated Data (AAD). This prevents ciphertext substitution attacks: even if two cards have the same PAN, their ciphertexts differ, and ciphertext cannot be transplanted from one card record to another.
2. **Blind Indexing (HMAC-SHA256):** Encrypted data cannot be searched directly with SQL `WHERE pan = ?`. To allow fast $O(1)$ lookups without decrypting the entire database table, a blind index (`pan_hash`) is generated by hashing the normalized PAN using HMAC-SHA256 with a dedicated, isolated secret key.
3. **Masked Display:** Only the first 6 digits (BIN) and last 4 digits are stored in plaintext (`411111******1111`) for UI display and receipt generation.

### Q21: How would cryptographic key management be implemented in an enterprise cloud production environment?
**Answer:**
- In local development, base64-encoded keys are injected via environment variables.
- In production:
  - Encryption keys (`keys.k1`) are managed by a Hardware Security Module (HSM) or cloud KMS (AWS KMS, Google Cloud KMS, or HashiCorp Vault).
  - **Envelope Encryption:** The application generates a local data encryption key (DEK) for card encryption. The DEK is encrypted under a KMS Key Encryption Key (KEK) and stored alongside the record.
  - **Key Rotation:** When rotating keys, a new key version (`k2`) is introduced. Decryption falls back to `k1` while all new writes use `k2`. A background re-encryption worker re-encrypts legacy records in batches without application downtime.
  - Plaintext keys never touch permanent disk or logs.

### Q22: What controls prevent sensitive data (PAN, CVV, passwords) from leaking into application logs?
**Answer:**
1. **Domain DTO Sanitization:** Sensitive input objects implement custom `toString()` methods or use Logback masking converters that redact any 13-to-19 digit card numbers using regex patterns.
2. **No CVV Retention:** The card verification value (CVV) is strictly validated in memory during card issuance or authorization and is immediately discarded. It is never persisted to database columns or logged.
3. **ArchUnit Static Verification:** Automated architectural test rules scan the compiled classes to ensure that sensitive properties are annotated with `@ToString.Exclude` (or excluded from record serialization) and that loggers do not print raw entity instances.

## 4. Architecture & Domain Modeling

### Q23: Why choose a Modular Monolith architecture over Microservices for this system?
**Answer:**
1. **ACID Transactions over Distributed Sagas:** Payment processing requires strict atomicity across card limits, balance ledgers, and idempotency records. In microservices, coordinating transactions across services requires distributed two-phase commits (2PC) or asynchronous saga choreography, which introduce partial failure modes, eventual consistency windows, and complex reconciliation pipelines.
2. **Zero Network Latency & Overhead:** Internal method calls execute in nanoseconds within memory, whereas distributed RPCs (REST/gRPC) introduce network serialization, latency spikes, and circuit breaker complexities.
3. **Operational Simplicity:** A single deployable artifact simplifies continuous deployment, database schema migrations (single Flyway pipeline), and local developer reproducibility.
4. **Boundary Enforcement:** Features are cleanly encapsulated into domain modules enforced by ArchUnit, leaving a frictionless path to carve out microservices later if scaling bottlenecks ever demand it.

### Q24: How does the Strategy Pattern enable extensible fraud rule evaluation?
**Answer:**
- Each fraud rule is an implementation of a common `FraudRuleEvaluator` interface:
  ```java
  public interface FraudRuleEvaluator {
      FraudRuleType getType();
      RuleEvaluationResult evaluate(AuthorizationRequest req, Card card, EvaluationContext ctx);
  }
  ```
- Concrete evaluators (`MaxAmountEvaluator`, `VelocityEvaluator`, `BlockedMccEvaluator`) encapsulate their own domain evaluation logic and dependencies (such as `AttemptCounter` for sliding velocity windows).
- The `FraudRiskEngine` injects `List<FraudRuleEvaluator>`, maps active rules from the database, executes applicable strategies in order, aggregates rule hits into `TransactionRuleHit` records, and determines whether the cumulative risk score triggers an outright decline, a transaction flag, or approval.
- Adding a new fraud rule (e.g., Geo-Velocity or High-Risk Country) requires writing a new class implementing `FraudRuleEvaluator` without modifying existing evaluators (Open/Closed Principle).

### Q25: How are Card and Dispute lifecycles modeled as deterministic State Machines?
**Answer:**
- **Card Lifecycle:** `PENDING_ACTIVATION` $\rightarrow$ `ACTIVE` $\rightleftharpoons$ `SUSPENDED` $\rightarrow$ `CLOSED`.
  - Once a card transitions to `CLOSED`, it enters a terminal state. No further status changes, top-ups, or ledger operations are permitted.
- **Dispute Lifecycle:** `OPEN` $\rightarrow$ `EVIDENCE_REQUESTED` $\rightarrow$ `UNDER_REVIEW` $\rightarrow$ `RESOLVED_WON` or `RESOLVED_LOST` (or terminal `CLOSED_AUTO`).
- **Enforcement:**
  - Transition validity is defined in enum maps or aggregate domain methods (`dispute.requestEvidence()`, `card.activate()`).
  - Attempting an illegal transition (e.g., attempting to win a dispute that is already closed) throws an `IllegalStateException` or custom `InvalidStateTransitionException`, which maps to HTTP 422 Unprocessable Entity.
  - Every valid transition appends an audit event to `dispute_event_log`, guaranteeing complete historical provenance.

### Q26: How does the background dispute sweeper handle multi-pod concurrency using `SKIP LOCKED`?
**Answer:**
When multiple instances of ATM Card Processor run concurrently behind a load balancer, background scheduled jobs (such as `DisputeDeadlineJob`) run on all nodes:
- If all nodes query overdue disputes using standard `SELECT ... WHERE deadline < NOW()`, they will pick up the same dispute records, causing lock contention and duplicate ledger credits.
- **PostgreSQL `FOR UPDATE SKIP LOCKED`:**
  ```sql
  SELECT * FROM dispute 
  WHERE status IN ('OPEN', 'EVIDENCE_REQUESTED') 
    AND deadline_at <= :now 
  ORDER BY deadline_at ASC 
  LIMIT 50 
  FOR UPDATE SKIP LOCKED;
  ```
- **Behavior:** Node 1 locks the first 50 rows. When Node 2 executes the query concurrently, PostgreSQL skips the rows currently locked by Node 1 without blocking, immediately returning the next 50 unlocked rows.
- Each dispute is processed within an isolated `REQUIRES_NEW` transaction boundary, ensuring that a failure in one dispute does not roll back the entire batch.

## 5. Frontend Architecture & UI Reliability

### Q27: When should you use Angular Signals versus RxJS Observables in modern Angular?
**Answer:**
- **Angular Signals (`signal()`, `computed()`, `effect()`):**
  - **Ideal for Local and Synchronous State:** Component UI state (dialog visibility, active tab, form dirty flags, selected filters, derived calculations like formatted totals).
  - **Fine-Grained Reactivity:** Signals track dependencies automatically at runtime and notify the Angular Zoneless / OnPush change detection engine exactly which DOM nodes need updating, eliminating dirty-checking cycles across entire component subtrees.
- **RxJS Observables (`Observable`, `Subject`, Operators):**
  - **Ideal for Asynchronous Event Streams & Orchestration:** Complex HTTP request pipelines, cancellation (`switchMap`), debounce intervals for search typeaheads (`debounceTime`), combining multiple independent asynchronous responses (`forkJoin`), and websocket streams.
  - In ATM Card Processor, HTTP calls originate as RxJS observables from `ApiClient` and are bridged cleanly into UI signals using `toSignal()` inside feature stores.

### Q28: How does the Auth Interceptor handle single-flight silent refresh without request flooding?
**Answer:**
When multiple components make concurrent API calls while the 15-minute access token is expired, all outgoing requests will receive HTTP 401 Unauthorized simultaneously:
- If every request independently attempted to refresh the token, 10 parallel refresh calls would be sent to the backend. The backend's token family reuse detector would see the first refresh succeed and subsequent refresh requests fail, triggering an accidental account session revocation.
- **Single-Flight Queuing Pattern:**
  - The `AuthInterceptor` detects the first 401 response and acquires a refresh lock (`isRefreshing = true`).
  - It triggers a single `POST /api/v1/auth/refresh` call.
  - Concurrent requests that encounter a 401 are held in an RxJS `BehaviorSubject` queue until the refresh completes.
  - Once the new access token is received, the interceptor replays all queued requests with the updated `Authorization: Bearer <newToken>` header. If the refresh call fails, all queued requests are rejected, and the user is redirected to `/login`.

### Q29: How does OpenAPI code generation prevent contract drift between frontend and backend?
**Answer:**
Manual TypeScript interface definitions frequently drift from backend Java DTOs when fields are added, renamed, or deprecated:
- In ATM Card Processor, the backend generates an accurate `openapi.json` specification from Spring Boot controllers using `springdoc-openapi`.
- The frontend runs `npx openapi-typescript ../docs/openapi.json -o src/app/core/api/v1.d.ts`.
- The generated TypeScript definitions strictly define request schemas, response types, query parameters, and enum values.
- If a Java developer renames a DTO field (e.g., `amountMinor` to `amountInCents`), running frontend typechecks (`npm run build`) immediately fails at compile time, catching interface mismatches before code reaches QA or production.

### Q30: How does the UI avoid duplicating backend business logic for state transitions?
**Answer:**
If the frontend independently determined whether to display buttons like "Request Evidence", "Resolve Won", or "Resolve Lost" based on hardcoded client logic, frontend and backend rules would inevitably diverge:
- **Backend HATEOAS / Action Enriched DTOs:** The backend API returns an `allowedActions` array inside response payloads:
  ```json
  {
    "id": "01946c10-...",
    "status": "EVIDENCE_REQUESTED",
    "allowedActions": ["SUBMIT_EVIDENCE", "RESOLVE_LOST"]
  }
  ```
- **Declarative UI:** The Angular template simply checks `dispute.allowedActions.includes('SUBMIT_EVIDENCE')`.
- If business rules evolve on the backend (e.g., prohibiting dispute resolution after 45 days), the UI automatically adapts without requiring frontend code changes.

## 6. Testing, Quality & Operational Scaling

### Q31: How was concurrency testing implemented to prove freedom from race conditions?
**Answer:**
Concurrency safety cannot be proven with single-threaded unit tests. Integration tests (`AuthorizationConcurrencyIT`) simulate high-load race conditions using `java.util.concurrent`:
1. **Balance Race Test:** 50 virtual threads are initialized against a card with an initial balance of NPR 10,000. Each thread attempts to authorize a payment of NPR 500 simultaneously. A `CountDownLatch` or `CyclicBarrier` aligns all threads to fire at the exact same millisecond.
   - *Verification:* Exactly 20 payments succeed, 30 fail with `INSUFFICIENT_FUNDS` (decline code 51). The final card balance is verified to be exactly NPR 0, and exactly 20 debit entries exist in the ledger. Not a single minor unit is over-spent.
2. **Idempotent Replay Race:** 10 threads send the exact same authorization payload with identical `Idempotency-Key` headers simultaneously.
   - *Verification:* Exactly one database authorization record and ledger entry are created; 9 requests receive the cached idempotent response; zero balance duplication occurs.

### Q32: What are the architectural limits of code coverage metrics (JaCoCo)?
**Answer:**
- While ATM Card Processor enforces strict JaCoCo coverage thresholds (>80% lines, >75% branches) and 100% mutation survival on financial math, code coverage only proves which lines of bytecode were executed by tests.
- **Coverage Does Not Guarantee:**
  - That edge cases or boundary values (e.g., integer overflow at `Long.MAX_VALUE`, negative minor units) were validated.
  - That concurrent database locks behave correctly under race conditions.
  - That distributed network latency, connection pool starvation, or clock skew were accounted for.
- True confidence requires layering unit tests with ArchUnit architectural rules, property-based testing, database concurrency integration tests, and Playwright end-to-end user journeys.

### Q33: If traffic grew from 10 TPS to 10,000 TPS, how would you evolve this system?
**Answer:**
1. **Stateless Horizontal Scaling:** Because Spring Boot nodes hold no in-memory user session state (JWTs are stateless, refresh tokens and idempotency records reside in PostgreSQL), backend application pods can scale horizontally behind an NGINX or AWS ALB ingress.
2. **Database Read Replicas & CQRS:** Operational queries and analytics (e.g., `ReportQueryRepository` generating dashboard charts and CSV exports) consume substantial CPU. Moving read-only queries to PostgreSQL streaming read replicas prevents analytics traffic from competing with authorization write locks on the primary database.
3. **In-Memory Distributed Caching for Reference Data & Rules:** Active fraud rules and card limit configurations can be cached in Redis with pub/sub cache invalidation, reducing database reads during the authorization critical path.
4. **Partitioning / Sharding by Card ID:** For extreme scale beyond a single PostgreSQL primary node, the card and ledger tables can be horizontally partitioned by hash of `card_id`, ensuring that row locks on independent cards never contend on the same database shard.
5. **Transactional Outbox Pattern & Event Streaming:** Asynchronous tasks (audit log shipping, notification emails, dispute webhooks) would be offloaded via an immutable outbox table scraped by Debezium into Apache Kafka, decoupling authorization latency from downstream consumers.
